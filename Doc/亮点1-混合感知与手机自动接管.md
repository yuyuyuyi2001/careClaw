# 亮点1：混合感知与手机自动接管

> 简历原文：基于无障碍树、截图与语音的混合感知，实现手机自动接管，Agent 能够自主完成决策、点击、验证全流程。同时实现误触保护与安全兜底，保障自动操作不失控。
>

## 1. 功能前因后果（为什么这样设计）

单靠一种感知拿不到完整世界，所以设计成"三通道互补"：

- **无障碍树（结构）**：`AccessibilityService` 能拿到当前界面的控件树（每个按钮/输入框的文字 + 坐标）。它"读得懂结构"，但拿不到真实像素——自定义绘制、视频、验证码等场景全是空白。
- **截图（像素）**：`MediaProjection` 拿到真实画面，视觉模型能"看懂"无障碍树看不懂的界面。但 MediaProjection 有个致命短板：Android 14+/ColorOS 等 OEM 上，**息屏或应用退后台时 token 会被系统瞬间 revoke**。所以补了一条 `AccessibilityService.takeScreenshot`（Android 11+）路径——不依赖 MediaProjection、无需弹窗，息屏也能截。
- **语音（意图）**：按住说话 → `AudioRecord` 录 PCM → 端侧本地 `LocalVoiceVisionHub` 直接做 STT + 意图理解。刻意**不依赖 Google SpeechRecognizer**（国产 ROM 不兼容），也没有固定 STT 模型，音频直接给多模态模型理解。

**为什么"接管"可行**：用户授权了无障碍权限后，系统就把 CareClaw 当作"无障碍辅助工具"（与 TalkBack 同类），于是服务拥有 `dispatchGesture()`（注入点击/滑动）、`performGlobalAction()`（返回/Home）、`performAction()`（对控件触发点击/输入文字）三个特权 API。**这是用户显式授权的通道，不是漏洞，也不是普通 App 天生就有**——这正是方案能成立的根基。

**为什么必须"验证"**：端侧模型是"看一步走一步"，每步执行后必须再截屏/读树确认界面真的变了，否则会盲目重复点击。所以 AgentLoop 是"快照→决策→执行→再快照→判断是否完成"的闭环。

    if (node == null) return false
    if (isDismissTarget(node)) return false          // "跳过/关闭/不感兴趣"不拦，允许关广告

    return false
}

## 5. 深挖点与应答

**Q1：无障碍树和截图都拿界面，为什么两套都要？**
答：互补。无障碍树有结构有坐标、token 便宜，但拿不到真实像素（自绘控件/视频/验证码读不出内容）；截图能让视觉模型"看懂"这些，但 MediaProjection 在息屏/退后台会被 OEM 撤销。所以正常态以树为主、截图辅证，息屏后切 A11y 截图。另外树能给 LLM 一个"可点击目标列表"，比让模型在整张图上猜坐标稳得多——这是端侧弱模型能跑起来的关键。

**Q2：dispatchGesture 注入的点击算"真实点击"吗？和 adb shell input tap 有什么区别？**
答：`dispatchGesture` 是 AccessibilityService 的系统级手势注入，效果等同真实触摸事件，目标应用无感知；它是 `AccessibilityNodeInfo` 之外最通用的操作方式，不要求目标控件有特定属性。相比之下 `adb input tap` 需要 adb/root 通道（遥控场景根本没有 adb），而 `performAction(ACTION_CLICK)` 对部分自绘控件不生效。所以选 dispatchGesture 做通用点击，输入文字用 ACTION_SET_TEXT（对 EditText 更可靠，且支持中文）。

**Q3：息屏后怎么还能截图和操作？这不会违反系统限制吗？**
答：这是 A11y 截图（`takeScreenshot`）区别于 MediaProjection 的核心——它由无障碍服务提供、不受 MediaProjection 的息屏/退后台 revoke 政策约束（代码注释明确写了动机）。代价是频率受限约每秒 1 张。这个设计正好回答"为什么无障碍是这套方案的地基"：息屏后继续干活靠的就是无障碍通道，截图、注入、读树全在它上面。

**Q4：广告误触防护误判了怎么办（把正常按钮当广告拦了）？**
答：三层兜底。① `device` 工具带 `ignore_ad_guard=true` 参数显式放行，把裁决权交还给 LLM 并注明"慎用"；② dismiss 文案白名单（跳过/关闭/不感兴趣）永不拦截，保证能关掉广告；③ 还有整屏级 `looksLikeAdvertisementScreen` 双命中打分，只在确凿时升级防御。取向是"宁可不点也不错点"——给老人用，点错装错 App 的代价远大于多花一轮重试。

**Q5：语音不依赖 Google STT，具体怎么做的？**
答：`VoiceRecorderManager` 用 `AudioRecord` 录 16kHz 单声道 PCM（`VoiceRecorderManager.kt:33-40`），录音结束后交给端侧 `LocalVoiceVisionHub` 直接做 STT + 多模态意图理解，整个链路不依赖任何固定识别模型，音频本身就是输入给 LLM 理解。这样国产 ROM（无 Google 服务）也能用，且"听语音→理解意图→触发任务"一步到位。

**Q6：怎么保证点完之后"装成功了"，而不是盲目往下点？**
答：两步。每轮工具执行后，下一轮迭代重新 `snapshot` 把新界面回填给 LLM，由模型判断"该 App 是否已在桌面上/安装完成"；同时 `ToolLoopDetection` 会对"同一操作重复无进展"做循环检测（详见亮点3），CRITICAL 直接熔断，防止 Agent 卡在某个弹窗反复点。安装链路里 `InstallAppSkill` 对 `STATUS_PENDING_USER_ACTION` 的兜底也保证了系统确认框阶段不会误操作。
