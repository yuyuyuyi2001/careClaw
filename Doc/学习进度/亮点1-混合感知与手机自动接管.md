## 一、功能前因后果（为什么三种感知）

单靠一种感知拿不到完整世界，三通道互补：

- **无障碍树（结构）**：`AccessibilityService` 拿界面控件树（文字+坐标）。读得懂结构，但拿不到真实像素——自定义绘制、视频、验证码全是空白。
- **截图（像素）**：`MediaProjection` 拿真实画面，视觉模型看懂树看不懂的界面。但 Android 14+/ColorOS 上**息屏或退后台时 token 被系统瞬间 revoke**，所以补 `AccessibilityService.takeScreenshot`（Android 11+）——不依赖 MediaProjection、无需弹窗、息屏也能截。
- **语音（意图）**：按住说话 → `AudioRecord` 录 PCM → 端侧 `LocalVoiceVisionHub` 做 STT + 意图理解。不依赖 Google SpeechRecognizer（国产 ROM 不兼容），音频直接给多模态模型理解。

**为什么"接管"可行**：用户授权无障碍权限后，服务拥有 `dispatchGesture()`（注入点击/滑动）、`performGlobalAction()`（返回/Home）、`performAction()`（触发点击/输入文字）三个特权 API。这是用户显式授权的通道，不是漏洞。

**为什么必须"验证"**：端侧模型"看一步走一步"，每步执行后必须再截屏/读树确认界面真的变了。所以 AgentLoop 是"快照→决策→执行→再快照→判断完成"闭环。

## 二、DeviceTool 核心操作（从「整体流程与核心机制」拆入）

总共 **16 个操作**，覆盖：读屏幕、点击、滚动、截图等。

```kotlin
when (action) {
    "snapshot"   → executeSnapshot(args)      // 拍屏幕快照（读控件树）
    "screenshot" → executeScreenshot(args)     // 截屏（像素图片）
    "act"        → executeAct(args)            // 执行操作（点/滑/打字...）基于 kind 路由
    "open"       → executeOpen(args)           // 打开 App
    "status"     → executeStatus()             // 查询设备状态
    "clipboard"  → executeClipboard()          // 读写剪贴板
}
```

**无障碍树**：`val viewNodes = proxy.dumpViewTree()` ← 调用 AccessibilityService 拿树

**核心亮点**：广告过滤、提示按钮防误触、ref 过期检测、包名一致性校验、自动弹窗关闭

> 广告过滤：广告控件关键词检查 + 广告内容文本匹配检查
> Ref 过期检测：每次使用无障碍树的 snapshot 时校验时间戳，**超过 20 秒就要去取新树**

## 三、关键链路（Observe→Reason→Act）

```
[Observe 感知]
  PhoneAccessibilityService.dumpView()                 accessibility/service/PhoneAccessibilityService.kt:124
    └─ 遍历无障碍树 → ViewNode[]（text/坐标/可点击等）
  SnapshotBuilder.buildFromViewNodes(ViewNode[])        agent/tools/device/SnapshotBuilder.kt:22
    └─ 转 Playwright 风格 RefNode（e1/e2...），压缩冗余节点
  device(action="snapshot") → DeviceTool.executeSnapshot
    └─ 截图：MediaProjectionHelper.captureScreen() 或 A11yScreenshotter.capture()（息屏兜底）
    └─ 组装 UI 树 + 截图路径 → 给 LLM

[Reason 决策]
  AgentLoop.callLlm → UnifiedLLMProvider（OpenAI 兼容 + SSE + 视觉）
    └─ LLM 返回 tool_call，如 device(action="tap", ref="e3")

[Act 执行]（带超时 + 广告防护）
  ToolCallDispatcher.execute → AndroidToolRegistry → DeviceTool.executeTap
    └─ resolveCoordinate(ref)：RefManager 解析坐标；REF_MAX_AGE_MS=20s 过期校验
    └─ AdUiGuard.isLikelyAdvertisement(node) 拦截疑似广告    agent/tools/device/AdUiGuard.kt:29
    └─ PhoneAccessibilityService.performClickAt(x, y)        PhoneAccessibilityService.kt:227
         └─ GestureDescription.Builder + dispatchGesture()  ← 系统级注入真实点击
    └─ 输入文字走 performAction(ACTION_SET_TEXT)             PhoneAccessibilityService.kt:286

[Verify 验证]
  下一轮迭代再次 snapshot → 对比界面变化 → 循环检测(ToolLoopDetection) → 判断完成/继续
```

**关键前置**：`onServiceConnected` 里把 `AccessibilityBinderService.serviceInstance` 设为本服务（`PhoneAccessibilityService.kt:47`），全项目多处直接拿这个单例做感知/注入。`onAccessibilityEvent` 监听 `TYPE_WINDOW_STATE_CHANGED` 实时记录前台包名/Activity（`:73`）——AccessibilityProxy 前台应用感知也复用它。

```kotlin
fun isLikelyAdvertisement(node: RefNode?): Boolean {
    if (node == null) return false
    if (isDismissTarget(node)) return false          // "跳过/关闭/不感兴趣"不拦，允许关广告
    val cls = node.className.orEmpty().lowercase()
    if (adClassFragments.any { cls.contains(it) }) return true   // ttad/gdt/pangle/ksad
    val text = node.text.orEmpty()
    if (adTextPhrases.any { text.contains(it, ignoreCase = true) }) return true
    return false
}
```

## 五、面试 QA

**Q1：无障碍树和截图都拿界面，为什么两套都要？**
答：互补。树有结构有坐标、token 便宜，但拿不到真实像素（自绘控件/视频/验证码读不出）；截图让视觉模型看懂这些，但 MediaProjection 息屏/退后台被 OEM 撤销。正常态树为主、截图辅证，息屏切 A11y 截图。树还给 LLM 一个"可点击目标列表"，比在整张图上猜坐标稳得多——这是端侧弱模型能跑的关键。

**Q2：dispatchGesture 注入算"真实点击"吗？和 adb input tap 区别？**
答：`dispatchGesture` 是 AccessibilityService 的系统级手势注入，效果等同真实触摸事件，目标应用无感知；不要求目标控件有特定属性。`adb input tap` 需要 adb/root 通道（遥控场景没有），`performAction(ACTION_CLICK)` 对部分自绘控件不生效。所以选 dispatchGesture 做通用点击，输入文字用 ACTION_SET_TEXT（对 EditText 更可靠、支持中文）。

**Q3：息屏后怎么还能截图和操作？**
答：A11y 截图（`takeScreenshot`）由无障碍服务提供、不受 MediaProjection 息屏/退后台 revoke 政策约束，代价是频率约每秒 1 张。息屏后继续干活靠的就是无障碍通道——截图、注入、读树全在它上面。

**Q4：广告误触防护误判了怎么办？**
答：三层兜底。① `device` 工具带 `ignore_ad_guard=true` 显式放行，把裁决权交还 LLM 并注明"慎用"；② dismiss 文案白名单（跳过/关闭/不感兴趣）永不拦截，保证能关广告；③ 整屏级 `looksLikeAdvertisementScreen` 双命中打分，只在确凿时升级。取向"宁可不点也不错点"。

**Q5：怎么保证点完之后"装成功了"，而不是盲目往下点？**
答：两步。每轮工具执行后下一轮迭代重新 snapshot 回填新界面给 LLM，由模型判断"是否安装完成"；`ToolLoopDetection` 对"同一操作重复无进展"做循环检测（详见亮点3），CRITICAL 直接熔断。安装链路 `InstallAppSkill` 对 `STATUS_PENDING_USER_ACTION` 有兜底。
