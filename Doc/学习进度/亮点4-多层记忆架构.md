## 一、架构：四类记忆文件（都在 workspace/memory/ 下）

| 文件 | 作用 | 上限 |
|---|---|---|
| `MEMORY.md` | **长期记忆**（入口1）：Agent 任务沉淀的操作经验/用户偏好/失败教训/项目上下文 | 16K 字符 |
| `IMAGE-MEMORY.md` | **相册记忆**（入口2）：扫描相册截图 → VLM 摘要 → 主题/内容索引，用于构建用户画像 | — |
| `USER-PROFILE.md` | **用户画像**：由长期记忆 + 相册记忆共同构建，默认加载进上下文 | 16K 字符 |
| `yyyy-MM-dd.md` | **每日日志**：Agent 每次任务事件先归档到当日日志，再进长期记忆 | — |

### 三个入口

1. **Memory Evolution** —— Agent 任务结束后自动触发记忆入队（`MainEntryNew.runWithSession()` 结束）→ 调用 `runEvolution` 批量更新记忆
2. **相册记忆** —— 独立的。用户手动点屏幕触发记忆更新，或 24h 定时任务
3. **记忆索引 + 记忆检索** —— agent 调用 `memory_search` 工具检索每日日志；`image_memory_search_entries` 检索画面

## 二、入口1：长期记忆 `MEMORY.md`

### 生产（写 pending 队列）

每次 Agent 流程处理完之后，`MainEntryNew.queueMemoryEvolutionEvent` → `MemoryEvolutionManager.recordAgentRun`（Agent 事件写入 `.memory-evolution-pending.jsonl`，等待后面写入 memory）。

> **核心设计意图**：防止单次任务污染长期记忆 —— 任务失败、异常、或者用户只是随便试试，这些事件都不会直接写进 `MEMORY.md`。它们先躺在 pending 队列里，等定时任务或用户指定来**批量审核**，通过 LLM 评判、敏感检测、去重三层过滤后才落地。

关键代码：
- 事件入队：`MainEntryNew.kt:761` `queueMemoryEvolutionEvent` → `MemoryEvolutionManager.recordAgentRun`（`MemoryEvolutionManager.kt:58-83`）
- 跳过自记录：`shouldSkipRunRecording`（进化任务自身不递归记录）
- 事件截断：userInput/finalContent/errorMessage 各 `take(1200)`，tools `distinct().take(12)`

### 消费（runEvolution 批量审核）

`MemoryEvolutionSkill.kt` → 调用 `manager.runEvolution()` → `MemoryEvolutionManager.runEvolution`（`MemoryEvolutionManager.kt:85-161`）：

1. `allEvents = readPendingEvents()` 去 jsonl 队列拿事件，`batch = allEvents.take(50)`（`maxPendingEventsPerRun`，默认 50）
2. **归档当日日志**：`memoryManager.appendToToday(formatDailyEvent(event))` 按事件时间写入 `yyyy-MM-dd.md`
3. **LLM 评判有价值的记忆**（4 类）：
   - `USER_PREFERENCE` 用户偏好（记住、我喜欢、不要等词汇）
   - `TASK_WORKFLOW` 可复用工作流（工具组合经验）
   - `FAILURE_LESSON` 失败经验（报错、权限问题等）
   - `PROJECT_CONTEXT` 关键项目上下文
4. **过滤**：
   - 敏感检测：`MemoryEvolutionPolicy.isSensitive`（密码、验证码、token、api key、银行卡等）
   - 去重：`distinctBy(category + normalizeForDedupe(title+content))`
5. `mergeGlobalMemory` 合并全局记忆（模板、记忆上限 16K）
6. 重建 `USER-PROFILE.md`，写回剩余 pending

### ⚠️ 2026-08 已改造：启发式评分 → LLM 评判

旧的「置信度阈值（confidence >= 0.55）+ 关键词启发式评分」已删除，改为 **`judgeMemory()` 用 LLM 直接评判**（`MemoryEvolutionManager.kt:179-232`）：

- 每个事件发给模型（system prompt 定义四类 + JSON 结构），返回 `{valuable, category, title, content}`
- 用 `chatWithTools(messages, tools=null, temperature=0.2, maxTokens=256, reasoningEnabled=false)` 调用
- `parseJudgeResult`：`JSON_BLOCK_RE`（`\{[\s\S]*?\}`）从回答里捞 JSON 块，`valuable=false` / 解析失败 → 返回 null（跳过该事件，不阻断整轮）
- `confidence` 固定为 1.0（不再启发式打分）

### 全局记忆合并（16K 上限）

- 4 个 section（对应四类）：`## 用户偏好与习惯` / `## CareClaw 任务经验与工作流` / `## 失败经验与绕过方式` / `## 长期项目上下文`
- 新条目格式：`- yyyy-MM-dd HH:mm:ss | title: content`
- `MemoryEvolutionPolicy.compactGlobalMemory(lines, maxChars=16000)` 超预算裁剪

## 三、入口2：相册记忆 `IMAGE-MEMORY.md`

### 触发

`GalleryMemoryWorkflow.syncGalleryMemories()`：每 24h 定时触发扫描，也可 UI 手动点击扫描。

> **相关背景**：安卓系统的底层相册索引管理用的是 SQLite，每张相册里的图片都有一个主键 id（MediaStore `_ID`）。

### 流程

**触发 → 游标扫描（MMKV 存索引位置）→ 去重 → 压缩 → VLM 调用摘要 → 隐私过滤 → 写入 image-memory → 建立 user-profile**

1. **触发入口**：`GalleryMemoryWorkflow.syncGalleryMemories()` 定时或 agent 手动
2. **游标扫描 + 去重 + 压缩**：`AlbumScanCursorStore.kt`、`AlbumScanner.kt`、`ImageMemorySummarizer.kt`
   - MMKV 存储：存时间戳（秒级）和图片 ID，**增量扫描**，不扫全表；MMKV 无过期时间
   - 游标双字段 `(DATE_MODIFIED, _ID)`，查询条件 `(modified > t) OR (modified = t AND _id > id)`，避免同秒多张图片丢失
   - 从已有的 `IMAGE-MEMORY.md` 去重，基于文件名（displayName）
   - 压缩图片 → 调 VLM（`ImageMemorySummarizer.buildVisionSummary`），系统提示词强调输出 JSON
   - JSON 形式：`{"summary":"...","extracted_text":"..."}`
   - **降级策略**：VLM 调用失败时，`buildFallbackSummary` 直接基于元数据生成摘要（面试可能问：VLM 不输出 JSON 咋办 → `JSON_BLOCK_RE` 正则提取 + 元数据兜底）
3. **数据脱敏**：`ImageMemoryPrivacyFilter` 正则匹配 + 身份证、银行卡、api、住址等关键字脱敏
4. **生成 image-memory.md**：`GalleryMemoryRepository.kt`

### ⚠️ 与代码核对后的格式修正

实际落盘格式（`AlbumImageRecord.toMarkdown()`）是 `time / album / summary`，**没有 keyWord 字段**（tags 字段在 data class 里但 toMarkdown 不输出）：

```markdown
# Image Memories

## IMG_20240813_123456.jpg
- time: 2024-08-13 12:34:56
- album: DCIM/Camera
- summary: 用户在餐厅拍摄的晚餐照片，桌上有一份牛排和红酒，环境温馨。
---
```

关键代码：
- 游标存储：`AlbumScanCursorStore.kt`（MMKV）
- 扫描：`AlbumScanner.scanNewImages`（增量游标，`AlbumImageRecord.kt:54-57`）
- 摘要：`ImageMemorySummarizer.summarize` → `buildVisionSummary`（VLM + JSON 解析）→ `buildFallbackSummary`（元数据兜底）
- 隐私：`ImageMemoryPrivacyFilter.sanitize`
- 落盘：`GalleryMemoryRepository.appendImageMemories`

## 五、入口3：记忆索引 + 记忆检索

> **相关背景**：安卓自带 SQLite，高版本自动支持 FTS5（BM25 全文检索）。SQLite 无向量支持，应用层手动暴力计算（余弦相似度）。

### 索引范围（2026-08-15 收窄）

**只索引两类文件**：
- `IMAGE-MEMORY.md`（画面）
- `yyyy-MM-dd.md`（按日日志）

`MEMORY.md` / `USER-PROFILE.md` / workspace 根 .md **不再进索引**，需要时用 `memory_get` 直接按文件读取。

改动代码：
- `MemoryManager.getAllMemoryFiles()`：只收画面 + 日志
- `MemoryManager.isIndexable()`：写入路径（writeMemory/appendToToday 等）也只索引这两类
- `MemorySearchSkill`：检索结果按 `\d{4}-\d{2}-\d{2}\.md` 正则过滤，**只返回日志**

### 索引构建

- 每日日志在 `appendToToday()` 触发构建，调用 `memoryIndex?.indexFile(logFile)`
- `IMAGE-MEMORY.md` 生成时触发构建
- `indexFile()`：
  1. 针对 filePath，捞 content
  2. 算 content 的 hash，相同 = 未改动，跳过；不同 = 需要更新
  3. update：切块（ChunkUtils）、embedding（可选）、双写：向量表 chunks 表 + FTS5 索引表
  4. 向量存储数据结构：BLOB（LE float32）
  5. FTS5 兼容性：部分旧 Android 机型没有 FTS5，降级到 LIKE 模糊搜索

### 检索（hybridSearch）

找照片和找日志**底层一样**（`MemoryIndex.hybridSearch`）：

- **向量检索 + BM25 关键词检索**。向量 0.7 + 关键词 0.3，按 `path:startLine` 去重 + 排序
- 候选 4 倍扩样（`DEFAULT_HYBRID_CANDIDATE_MULTIPLIER=4`），低于 `minScore=0.35` 过滤
- 向量未配置（无 embedding key）时退化为纯关键词
- **索引没结果降级为内存扫描**：载入 `IMAGE-MEMORY.md` 扫描 summary/displayName/album（`ImageMemorySearchEntriesSkill.retrieveMatchedEntries` 兜底）

### 检索触发（两个工具分工）

| 场景 | 工具 | 检索对象 |
|---|---|---|
| 找照片 | `image_memory_search_entries` | IMAGE-MEMORY.md |
| 微信安装失败看原因 | `memory_search` | yyyy-MM-dd.md 日志 |

关键代码：
- 索引核心：`MemoryIndex.kt`（SQLite 三表 files/chunks/chunks_fts + hybridSearch）
- 向量：`EmbeddingProvider.kt`（远程 /embeddings，`isAvailable` 由 apiKey 决定）
- 工具：`MemorySearchSkill.kt`（日志）、`ImageMemorySearchEntriesSkill.kt`（画面）、`MemoryGetSkill.kt`（整文件读取）

## 七、面试 QA（模拟面试官拷打）

**Q1：记忆系统为什么分三个入口？为什么不直接都走 LLM 生成 markdown？**
答：三个入口对应三条数据源和三种触发时机。入口1（Memory Evolution）管 Agent 任务经验，是"任务结束后异步沉淀"，走 pending 队列防污染；入口2（相册记忆）管非结构化的图片，需要独立的扫描→VLM 摘要→脱敏→落盘管线，因为图片本体模型读不完；入口3（记忆索引+检索）是查询侧，把已落盘的 md 分块建索引，让 LLM 按语义检索而非整文件读入。分三套是为了职责单一、解耦写侧与查侧。

**Q2：为什么任务结束不直接写长期记忆，要先进 pending 队列？**
答：两个原因。一是防污染——失败/异常/随口试试的事件直接写进 MEMORY.md 会污染长期画像，所以先入 jsonl 队列，由 runEvolution 批量用 LLM 评判（valuable 才要）+ 敏感词拒收 + 标题去重三层过滤后落地。二是批量合并要控制上下文预算——MEMORY.md 上限 16K，每批最多处理 50 条事件，压缩合并。`shouldSkipRunRecording` 还防止"进化任务自身"被递归记录。

**Q3：LLM 评判（judgeMemory）具体怎么做？它失败怎么办？**
答：每个 pending 事件把 userInput+finalContent 发给模型，system prompt 定义四类记忆（用户偏好/任务工作流/失败教训/项目上下文）和 JSON 输出结构 `{valuable, category, title, content}`。用 `chatWithTools(tools=null, temperature=0.2, maxTokens=256)`，温度低保证判断稳定。`parseJudgeResult` 用 `JSON_BLOCK_RE` 正则从模型回答里捞 JSON 块，valuable=false 或解析失败返回 null——**单条失败跳过该事件，不阻断整轮进化**。这替代了旧版的"confidence>=0.55 + 关键词启发式评分"。

**Q4：相册增量扫描怎么保证不重复、不丢图？**
答：双字段游标 `(DATE_MODIFIED, _ID)`，查询 `(modified > t) OR (modified = t AND _id > id)`，解决同秒多张图；游标推进取本批最大值存 MMKV。从新到旧排序每批扫 20 张，以 displayName 为主键与已有 IMAGE-MEMORY.md 去重。`force_rescan=true` 可重置游标全量重扫。

**Q5：VLM 不输出 JSON 咋办？（面试高频）**
答：两道兜底。①`ImageMemorySummarizer` 用 `JSON_BLOCK_RE` 正则从模型文本里提取 JSON 块再解析，不严格要求纯 JSON 输出；②VLM 整体失败时 `buildFallbackSummary` 直接基于图片元数据（文件名/时间/相册/宽高）生成摘要，保证扫描流程不中断。隐私过滤在摘要之后统一做。

**Q6：记忆检索为什么只索引画面和日志？MEMORY.md 和画像怎么被找到？**
答：检索收窄为「画面 + 日志」两域，因为这两个是"增长型、需要按内容找"的数据（图片多了不能全量读、日志是按天累积的）。MEMORY.md（16K 封顶）和 USER-PROFILE.md（16K 封顶）体量可控，直接由 ContextBuilder bootstrap 按预算注入或 memory_get 整文件读取，不需要建索引——省掉 SQLite 索引维护成本。找照片走 `image_memory_search_entries`（画面域），找历史任务走 `memory_search`（日志域），分工明确。

**Q7：向量检索是端侧的吗？Embedding 从哪来？**
答：检索计算在端侧——SQLite 存向量 BLOB + Kotlin 手写余弦相似度全表扫描。但**向量本身由远程 API 生成**：`EmbeddingProvider` 走 OkHttp 调 OpenAI 兼容 `/embeddings`（默认 text-embedding-3-small），`isAvailable` 由 apiKey 是否非空决定。无网/无 key 时自动降级为纯关键词（FTS5/LIKE）。**"端侧"只对检索成立，向量生成和 VLM 摘要都是远程的**——面试要主动澄清这点。

**Q8：画像（USER-PROFILE）构建的 4 个来源是什么？怎么保证不泄漏隐私？**
答：来源是 IMAGE-MEMORY.md、近 3 天日志、MEMORY.md、AGENTS.md，用规则聚合（标签统计+关键词推断）生成 9 维画像。隐私三道防线：①VLM system prompt 要求摘要避免输出身份证/手机/银行卡等敏感字段；②`ImageMemoryPrivacyFilter` 落盘前正则脱敏 + 高风险关键词判 sensitivity=high；③`MemoryEvolutionPolicy.isSensitive` 对候选全局记忆拒收密码/验证码/token/api key 类。

**Q9：为什么 SQLite 不用原生向量扩展，而是全表扫描算余弦？**
答：SQLite 没有向量支持，FTS5 只做关键词；加原生向量扩展（如 sqlite-vec）要引第三方 so 库，增加 APK 体积和兼容性风险。项目规模下记忆文件很小（几十 KB），全表扫描 + 手写余弦相似度 O(n) 完全可接受，换取零额外依赖、纯 Kotlin 可维护。
