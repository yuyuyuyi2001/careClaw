## 一、为什么拆成双注册表（Tool / Skill 同构双接口）

核心文件：

```
agent/tools/Tool.kt                  ← 通用工具接口（+ typealias ToolResult = SkillResult）
agent/tools/Skill.kt                 ← 平台技能接口 + SkillResult
agent/tools/ToolRegistry.kt          ← 通用注册表
agent/tools/AndroidToolRegistry.kt   ← Android 注册表
agent/tools/ToolCallDispatcher.kt    ← 统一分发（唯一执行入口）
```

**为什么是"双"**：参考 OmniClaw 的 pi-tools 分层——通用能力（文件/配置/网络）跨平台可复用，Android 平台能力（点屏/装包/记忆）与设备强耦合。拆两个注册表让职责单一，按需装配时过滤逻辑也各自清晰。

**同构接口**：Tool 和 Skill 长得一模一样，四个要素：

```kotlin
interface Tool {
    val name: String                        // 工具名（对应 function name）
    val description: String                 // 给人/模型看的描述
    fun getToolDefinition(): ToolDefinition // 出入参 JSON Schema（让 LLM 知道怎么调用）
    suspend fun execute(args: Map<String, Any?>): SkillResult  // 真正干活
}
typealias ToolResult = SkillResult          // 两种工具共用同一个结果契约
```

> **关键**：Tool 与 Skill 结构同构、结果同型（`typealias ToolResult = SkillResult`），上层 `ToolCallDispatcher` 才能无差别分发、`getToolDefinitions` 才能合并返回——这是"双注册表却能统一调用"的前提。

## 三、典型工具实现：InstallAppSkill 六步走

[InstallAppSkill.kt](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/tools/InstallAppSkill.kt) 是最标准的技能写法，`execute()` 里每步一个注释块，分层清晰：

```kotlin
override val name = "install_app"
override val description = "Install/upgrade APK from local path or content://. See getToolDefinition LLM block."

override fun getToolDefinition(): ToolDefinition { /* 出入参规范：apk_path 必填(string) + allow_downgrade 可选(boolean) */ }

override suspend fun execute(args: Map<String, Any?>): SkillResult {
    // ===== 1. 参数解析 =====   apk_path 缺失/类型不对 → 直接返回错误
    // ===== 2. 解析 APK 文件 =====   content:// URI 拷到 cacheDir；本地路径常见前缀兜底（/sdcard/Download/...）
    // ===== 3. 从 APK 解析包信息 =====   getPackageArchiveInfo（不装也能读 manifest，longVersionCode 按 API 分版本取）
    // ===== 4. 检查是否已安装 =====   getPackageInfo，NameNotFoundException → null
    // ===== 5. 判定安装类型 =====   upgrade / reinstall / downgrade / fresh；降级默认禁止，需 allow_downgrade=true
    // ===== 6. 执行安装并返回结果 =====   performInstall：PackageInstaller 会话式安装 + withTimeout(60s)
}
```

**安装实现要点（performInstall）**：
- `PackageInstaller` 会话式安装：`createSession` → `openSession` → `openWrite` 写入 APK → `fsync` → `commit`
- API 31+ 设 `setRequireUserAction(USER_ACTION_NOT_REQUIRED)` 尝试静默安装
- 收结果用 BroadcastReceiver + `suspendCancellableCoroutine` 挂起协程，超时/取消时 `session.abandon()` 兜底
- `STATUS_PENDING_USER_ACTION` 时拉起系统确认弹窗，并提示 LLM 用 screenshot/tap 配合交互
- 成功返回带元数据（包名/版本/安装类型/APK 大小），供 LLM 给用户展示

## 四、统一分发 ToolCallDispatcher（策略模式）

[ToolCallDispatcher.kt:28-51](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/tools/ToolCallDispatcher.kt#L28-L51) 是所有 tool_call 的**唯一入口**，用名字查两个注册表，命中即分发：

```kotlin
fun resolve(name: String): DispatchTarget? = when {
    toolRegistry.contains(name)         -> DispatchTarget.Universal(name)
    androidToolRegistry.contains(name)  -> DispatchTarget.Android(name)
    else -> null
}
suspend fun execute(name, args) = when (val target = resolve(name)) {
    is DispatchTarget.Universal -> toolRegistry.execute(name, args)
    is DispatchTarget.Android   -> androidToolRegistry.execute(name, args)
    null -> SkillResult.error("Unknown function: $name")
}
```

> 核心价值：**AgentLoop 不需要知道某个名字属于哪个注册表**，只管调 `dispatcher.execute(name, args)`。新增工具 = 注册进对应注册表，零侵入。

## 五、按需装配 + 智能路由

工具分两类（[LlmOnDemandToolInclusion.kt:11-33](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/tools/LlmOnDemandToolInclusion.kt#L11-L33)）：

- **常驻工具**：schema 每轮都带
- **按需工具 ON_DEMAND**（18 个里的大多数，含 device / install_app / 记忆类等）：**默认不进 LLM 的 tools**，只有本轮命中才注入

`getToolDefinitions(onDemandLlmNamesToInclude)`（两个注册表都有）：on-demand 工具只有 `name in onDemandLlmNamesToInclude` 才出 schema。

### 首跳路由（[AgentLoop.kt:76-128](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/loop/AgentLoop.kt#L76-L128)）

```
用户输入
  ├─ 寒暄？（isGreetingOnlyMessage）→ tools=[] 直接发，省 token
  └─ 工具路由：
      ① LlmToolRouter.runRouterLlm   ← 小模型首跳（tools=null, temp 0.1, maxTokens 420）
         · 输入：可路由工具名清单 + 用户问题 + system prompt 片段
         · 输出：{"tools":[...], "hint":"..."}（hint 给主 Agent 做级联线索）
         · 优先后者
      ② 解析失败/超时 → 降级 LlmOnDemandToolInclusion.resolveInclusions 关键词启发式
```

- **可路由名单**：`buildRoutableNameList` = `ON_DEMAND ∩ 已注册`，防止路由推荐到没注册的工具
- **关键词启发式**：每个工具一组 `wantsXxx()` 规则，如"安装/装应用/.apk"→ `install_app`；"照片/截图/图库"→ `image_memory_search_entries`；"记忆/回忆/以前/记住"→ `memory_get/memory_search`；"定时/提醒/闹钟"→ `schedule_task`；"蓝牙/WiFi/亮度/飞行"→ `system_settings`
- **hint 注入**：路由结果塞进 system prompt 的 `[RouteHint 供主 Agent 参考, 非硬约束]`

## 六、循环检测 ToolLoopDetection（安全控制）

每轮工具执行**前**先检测（[AgentLoop.kt:347-365](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/loop/AgentLoop.kt#L347-L365)），历史记录在 `SessionState`（ArrayDeque，上限 30 条）。四种检测按优先级：

| 检测 | 阈值 | 触发条件 |
|---|---|---|
| `GLOBAL_CIRCUIT_BREAKER` 全局熔断 | ≥20 | 同工具+同参数+**同结果**无进展，直接 CRITICAL（最高优先级、最狠） |
| `KNOWN_POLL_NO_PROGRESS` 轮询空转 | 10 / 20 | wait / wait_for_element / command_status 同参无进展：10 次 WARNING，20 次 CRITICAL |
| `PING_PONG` 乒乓 | 10 / 20 | a-b-a-b 交替且结果无进展：10 次 WARNING，20 次 CRITICAL |
| `GENERIC_REPEAT` 通用重复 | ≥10 | 同工具同参重复，仅 WARNING 一次（不熔断） |

**WARNING vs CRITICAL 的处理**（[AgentLoop.kt:348-365](CareClaw/app/src/main/java/com/shijing/xomniclaw/agent/loop/AgentLoop.kt#L348-L365)）：

- **WARNING**：把英文提醒作为 tool 消息**回填给 LLM**（"停止重试，换个操作或报失败"），循环继续；`reportedWarnings` 按 warningKey 去重，**每个 key 只提醒一次**
- **CRITICAL**：回填后 `finalContent = "Task failed: ..."`，`shouldStopLoop = true` **直接熔断整轮对话**

**判重核心**：`hashToolCall` 对 (工具名 + 参数) 做 SHA-256（参数先 `stableStringify` 排序键）；`hashToolOutcome` 对结果取前 500 字符哈希。**同工具同参只是基础，真正决定"无进展"的是结果哈希连续相同**——参数一样但结果在变（如轮询等待中），不算无进展。

## 八、面试 QA

**Q1：Tool 和 Skill 接口长得一样，为什么还要拆两个注册表？**
答：语义和归属不同。Tool 是跨平台通用能力（读文件、读写配置），Skill 是 Android 平台业务能力（点屏、装包、记忆）。拆开的好处：①通用层与设备解耦、可独立复用；②`getToolDefinitions` 的 on-demand 过滤逻辑各自维护；③类名约定（*Skill）一眼看出平台归属。靠 `typealias ToolResult = SkillResult` 统一结果契约，分发表才能无差别调用。

**Q2：为什么多数工具默认不给 LLM 提供 schema，要按需装配？**
答：token 与准确率。18 个工具全量 schema 每轮都占上下文预算，端侧模型窗口更紧张，且多数工具一轮对话根本用不到。所以 ON_DEMAND 集合默认不进 tools，只有路由判定"本轮可能用"才注入。代价是首跳多一次小模型路由调用，但那次 tools=null、maxTokens 只有 420，很便宜。

**Q3：路由为什么优先小模型、关键词只做降级？**
答：关键词是硬规则，覆盖不了自然语言变体（如"帮我找找上次那张照片"没有"记忆"二字）。小模型首跳给紧凑工具清单做语义判断，还能返回 hint（搜索词、app 名猜测）级联给主 Agent。但它可能解析失败/超时/乱输出，失败就降级关键词，双保险。另外寒暄直接短路 tools=[]，连路由都不跑。

**Q4：循环检测四种模式分别防什么？怎么协同？**
答：全局熔断防"卡死但一直重试"（同参同结果无进展≥20）；轮询空转防 wait 类工具原地打转（10 次警告给模型自救机会）；乒乓防两个工具互相倒腾不前进；通用重复兜底"同工具同参刷屏"。设计意图是**先 WARNING 让模型自己修正，修正不了再 CRITICAL 熔断止损**，避免一棒子打死合法重试。

**Q5：怎么判断"无进展"？只看参数一样够吗？**
答：不够。参数一样但每次结果在变（比如轮询等待中），说明有进展、不该熔断。所以 `recordToolCallOutcome` 把结果哈希（前 500 字符）也记进历史，`getNoProgressStreak` 从尾部往前数"参数相同 + 结果哈希连续相同"才算无进展，结果一变就 break 重新计数。

**Q6：WARNING 和 CRITICAL 为什么处理不一样？**
答：WARNING 是"提醒修正"，把提示作为 tool 消息注入下一轮 LLM 输入（带 warningKey 去重、只提醒一次），让模型换个策略；CRITICAL 是"止损"，`shouldStopLoop=true` 直接结束本轮 agent、finalContent 记为 Task failed，防止空转烧 token。分级保证合法重试不被误杀，同时失控时一定停得下来。
