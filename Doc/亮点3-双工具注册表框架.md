# 亮点3：双工具注册表框架

> 简历原文：设计可扩展的双工具注册表框架，支持通用工具与 Android 平台工具的按需装配与智能路由，配合循环检测与误触保护，保证自动操作的安全可控。
>
> 代码根：`e:\aqiuzhao\myClaw\CareClaw\app\src\main\java\com\shijing\xomniclaw\`（下文路径相对该目录）。

---

## 1. 功能前因后果（为什么这样设计）

端侧智能体要把"会操作 Android"的能力暴露给 LLM，最朴素做法是把所有工具 schema 一次性塞进 `tools` 参数。但 CareClaw 工具面很宽（device 一个工具就带 20+ 参数、安装、记忆检索、图库、系统设置……），全量注入有两个致命问题：

1. **Token 开销大**：端侧上下文有限，每次迭代背全套 schema 浪费大量预算，"你好"这种寒暄也要带满工具。
2. **误导性**：工具越多模型越容易选错；像 `memory_evolution`（相册扫描→摘要→画像）这种重工具根本不该出现在候选里。

设计分层（对应 X-OmniClaw 的 pi-tools 思想）：
- **抽象统一**：`Tool` 与 `Skill` 是**同名同构**的两个接口（name/description/getToolDefinition/execute），返回结果共用 `SkillResult`（`typealias ToolResult = SkillResult`）。区别只是语义定位：Tool 是跨平台低层能力（读文件、配置），Skill 是 Android 专属业务能力（点屏、装 App）。`DeviceToolSkillAdapter` 把实现 `Tool` 的 `DeviceTool` 包成 `Skill` 塞进 Android 注册表，证明两接口只是形式差异。
- **双注册表分工**：`ToolRegistry`（通用：read_file/config_get/config_set）+ `AndroidToolRegistry`（平台：device/install_app/memory_*/stop/selfcontrol 系列）。
- **统一分发**：`ToolCallDispatcher` 用 sealed class `DispatchTarget` 把 tool_call 按名字路由到两个注册表，AgentLoop 不再关心归属。
- **按需装配**：`LlmOnDemandToolInclusion` 定义"高 token 成本工具"默认不暴露 schema，靠关键词启发式（或 `LlmToolRouter` 首跳 LLM 路由）决定当轮注入哪几个。
- **安全可控**：执行层 `AdUiGuard` 广告拦截 + ref 过期校验；指令层 `SafetyPolicy` 白名单 + 高危二次确认 + 审计；失控兜底 `ToolLoopDetection` + `EmergencyStopSkill`。

一句话：**抽象统一、注册分离、分发单一、暴露按需、执行带防**。

## 3. 核心代码片段

**① Tool 抽象接口——统一"可被 LLM 调用的能力"的契约** — `Tool.kt:25-47`
```kotlin
interface Tool {
    val name: String                // 工具名（即 LLM function name）
    val description: String         // 描述，参与 system prompt
    fun getToolDefinition(): ToolDefinition   // 生成 function calling 的 schema
    suspend fun execute(args: Map<String, Any?>): ToolResult   // 执行，返回 SkillResult
}
typealias ToolResult = SkillResult   // Tool 和 Skill 共享同一 Result 类型
```

**② 统一分发器——一个 tool_call 路由到正确的注册表** — `ToolCallDispatcher.kt:28-51`
```kotlin
fun resolve(name: String): DispatchTarget? {
    return when {
        toolRegistry.contains(name) -> DispatchTarget.Universal(name)      // 通用注册表
        androidToolRegistry.contains(name) -> DispatchTarget.Android(name) // 平台注册表
        else -> null
    }
}
suspend fun execute(name: String, args: Map<String, Any?>): SkillResult {
    return when (val target = resolve(name)) {
        is DispatchTarget.Universal -> { toolRegistry.execute(target.name, args) }
        is DispatchTarget.Android  -> { androidToolRegistry.execute(target.name, args) }
        null -> SkillResult.error("Unknown function: $name")
    }
}
```

**③ 按需装配——高 token 工具默认不进 prompt，命中关键词才注入** — `LlmOnDemandToolInclusion.kt:11-34, 82-127`
```kotlin
val ON_DEMAND_LLM_TOOL_NAMES: Set<String> = setOf(
    "read_file", "config_get", "config_set",        // 通用工具（按需）

    "image_memory_search_entries", "gallery_memory", "memory_evolution",
    "system_settings", "memory_get", "memory_search",

    "install_app", "copy_images_to_album", "list_gallery_images"

fun resolveInclusions(systemPrompt: String, userMessage: String): Set<String> {
    val uLow = userMessage.lowercase()

    if (wantsMemoryGetSearch(u, low, sys)) { out.add("memory_get"); out.add("memory_search") }
    ...
    return out
}
```

```kotlin
private const val TOOL_CALL_HISTORY_SIZE = 30    // 环形历史，只记最近 30 次
```

## 4. 面试常用描述（可口头背诵，~115 字）

> "我把智能体能力抽象成统一的 Tool 接口，按跨平台通用和 Android 平台分成两个注册表，用一个分发器统一路由 LLM 的工具调用。高 token 的工具默认不进 prompt，靠首跳 LLM 路由器加关键词启发式按需装配。执行层有广告和提示按钮误触防护，外加四类循环检测兜底，被拦就回填警告让模型改思路，CRITICAL 直接熔断；远程指令还有白名单和高危二次确认。"

## 5. 深挖点与应答

**Q1：既然 Tool 和 Skill 接口完全一样，为什么非要分两个注册表？**
答：一是职责清晰——通用工具（读文件/配置）跨平台可复用，Android 工具强依赖无障碍服务与系统 API，分开注册便于按能力裁剪；二是 schema 组装时按类别生成 system prompt 描述（AndroidToolRegistry 按"屏幕与交互/应用管理/记忆"分类）；三是执行路径解耦，通用注册表可复用 X-OmniClaw 的 Pi 工具生态。技术上可合并，但语义分层带来更好的可维护性和 token 控制。`DeviceToolSkillAdapter` 的存在正好说明架构允许跨接口。

**Q2：按需装配为什么要"LLM 路由 + 关键词启发式"两层？一层不够吗？**
答：关键词启发式零延迟零成本、规则可解释，但覆盖不了"换个说法"的输入；LLM 路由理解语义更准，但要多一次 420 token 的 LLM 首跳。设计是 **LLM 优先、失败自动降级**：router 解析失败/异常就回退关键词，`ENABLED=false` 时纯走关键词。寒暄检测（`isGreetingOnlyMessage`）在两层之前短路，直接 `tools=[]`，把"你好"这种输入的 token 压到最低。

**Q3：四类循环检测分别防什么场景？阈值怎么定的？**
答：GENERIC_REPEAT 防"同一工具同参重复刷"（≥10 次告警）；KNOWN_POLL_NO_PROGRESS 专治 wait/wait_for_element 这类轮询工具空转；PING_PONG 防两个工具来回交替（用 argsHash 交替尾部计数 + 结果哈希无进展佐证）；GLOBAL_CIRCUIT_BREAKER 是最后防线（同参同结果连续 30 次直接 CRITICAL 熔断）。关键设计是**哈希按工具名+参数+结果三元组判"无进展"**，所以"结果在变"的动作不会误判。`ToolLoopDetectionTest` 单测存在，可作为"循环检测有回归测试"的佐证。

**Q4：广告误触防护如果误判（把正常按钮当广告）怎么办？**
答：三道兜底——`ignore_ad_guard=true` 参数显式放行（把选择权交还 LLM 并注明"慎用"）；dismiss 文案白名单（跳过/关闭/不感兴趣）永不拦截；整屏级 `looksLikeAdvertisementScreen` 双命中打分只在确凿时升级。取向是"宁可不点也不错点"，符合给父母用的场景。

**Q5：高危操作"二次确认"在代码里到底怎么落地？**
答：`SafetyPolicy.checkRemoteCommand` 对含 install/uninstall/send/pay 的指令返回 `requireConfirm=true`，网关在回执里带 `requireConfirm` 字段，由**对端（子女/飞书侧）收到后回复"确认"才真正下发执行**——确认逻辑在交互层而不是端上，端上只做标记与审计。同时 `InstallAppSkill` 内部还有第二重防线：PackageInstaller 无法静默时返回 `STATUS_PENDING_USER_ACTION`，弹系统确认框。所以是"远程确认 + 系统安装确认"双层。

**Q6：现在要新增一个工具（比如"一键清理内存"），需要动哪些地方？**
答：①写一个实现 `Skill`（或 `Tool`）的类，定义 name/description/getToolDefinition（JSON schema）/execute；②在 `AndroidToolRegistry.registerAndroidTools` 里 `register(...)`；③如果在 ON_DEMAND 集合就放进 `ON_DEMAND_LLM_TOOL_NAMES` 并加一条 `wantsXxx` 关键词规则（或靠 LlmToolRouter 路由）；④高耗时工具（如 gallery_memory）在 `AgentLoop.toolExecutionTimeoutMs` 加超时分支；⑤高危操作在 `SafetyPolicy.HIGH_RISK_ACTIONS` 登记。这正体现"注册即生效、暴露按需"的可扩展设计。
