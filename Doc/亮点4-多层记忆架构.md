# 亮点4：多层记忆架构

> 简历原文：设计多层记忆架构，通过工作记忆 + 相册主题检索 + 画像进化，实现向量相似度匹配与上下文增强，沉淀长期用户画像。
>

## 1. 功能前因后果（为什么这样设计）

核心痛点：会话级上下文窗口有限、LLM 无持久记忆、端侧算力/预算受限。多层记忆把"用户是谁、关心什么、任务怎么做过"沉淀下来，后续会话按需回放，而不是每次冷启动。

- **工作记忆（MemoryManager + MemoryIndex）**：解决"长期记忆文件怎么写、运行时怎么找回"。所有记忆最终是 workspace 里的 markdown（`MEMORY.md`、`memory/YYYY-MM-DD.md`、`IMAGE-MEMORY.md`、`USER-PROFILE.md`）。为了让 LLM 按语义检索而非整文件读入，把 md 分块后建 SQLite 索引，同时做 **FTS5 关键词 + 向量余弦相似度 hybrid search**，结果带得分和行号回填。
- **相册记忆（Gallery Memory）**：解决"相册上万张图，模型读不完也看不懂"。MediaStore 增量扫描 → VLM 生成图片摘要 → 隐私脱敏 → 紧凑 markdown 落盘 → 聚合用户画像。图片本体不存，只存语义摘要，检索在摘要文本上做 hybrid search。
- **画像进化（Memory Evolution）**：解决"记忆不能每轮任务直接污染长期记忆"。任务结束只把事件写入 **pending 队列**，由 `memory_evolution` 定时任务（默认 24h）批量把"偏好/可复用任务/失败经验/项目上下文"四类候选聚合进 `MEMORY.md`，同时重建 `USER-PROFILE.md`。

整体一条流水线：**Observe（扫描/任务）→ Reason（VLM 摘要/候选抽取）→ 沉淀（markdown 落盘 + 索引）→ 回放（bootstrap 注入 + 按需检索）**。

## 3. 核心代码片段

**① Hybrid search 合并策略（向量 0.7 + 关键词 0.3，按 path:startLine 去重）** — `MemoryIndex.kt:297-351`
```kotlin
suspend fun hybridSearch(query, maxResults, minScore): List<SearchResult> {
    val candidateLimit = maxResults * DEFAULT_HYBRID_CANDIDATE_MULTIPLIER   // 候选 4 倍扩样
    val vectorResults = if (embeddingProvider?.isAvailable == true) {
        val qe = embeddingProvider.embed(query)
        if (qe != null) searchVector(qe, candidateLimit) else emptyList()
    } else emptyList()
    val keywordResults = searchKeyword(query, candidateLimit)                // FTS5 / LIKE
    if (vectorResults.isEmpty()) return keywordResults.filter { it.score >= minScore }.take(maxResults)
    val merged = mutableMapOf<String, SearchResult>()
    for (r in vectorResults) {
        val key = "${r.path}:${r.startLine}"
        val vectorScore = r.score * DEFAULT_HYBRID_VECTOR_WEIGHT            // 0.7
        merged[key] = merged[key]?.copy(score = it.score + vectorScore) ?: r.copy(score = vectorScore)
    }
    for (r in keywordResults) { /* 同样，权重 DEFAULT_HYBRID_TEXT_WEIGHT = 0.3 */ }
    return merged.values.filter { it.score >= minScore }
        .sortedByDescending { it.score }.take(maxResults)
}
```

private fun cosineSimilarity(a: FloatArray, b: FloatArray): Float {
    var dot = 0f; var magA = 0f; var magB = 0f
    for (i in a.indices) { dot += a[i]*b[i]; magA += a[i]*a[i]; magB += b[i]*b[i] }
    val denom = sqrt(magA) * sqrt(magB)
    return if (denom < 1e-10f) 0f else dot / denom
}

    val batch = readPendingEvents().take(settings.maxPendingEventsPerRun)  // pending jsonl

## 5. 深挖点与应答

**Q1：向量检索是纯端侧吗？Embedding 用什么模型？**
答：检索是端侧的（SQLite 存向量 BLOB + Kotlin 手写余弦相似度全表计算），但**向量本身是远程生成的**：`EmbeddingProvider` 走 OkHttp 调 OpenAI 兼容 `/embeddings`，默认 `text-embedding-3-small`，返回 L2 归一化向量。`isAvailable` 由 apiKey 是否非空决定。**"纯端侧"只对检索成立**；无网络/无 key 时自动降级为 FTS5/LIKE 纯关键词检索。面试建议主动澄清这点，体现诚实。

**Q2：hybrid search 怎么合并向量分和关键词分？会不会有偏置？**
答：先各自按 4 倍扩样取候选，以 `path:startLine` 为 key 去重合并，权重向量 0.7 / 关键词 0.3，低于 `minScore=0.35` 的过滤，按总分排序截断。关键词侧用 BM25（FTS5）或 LIKE 命中率归一化。隐患是向量没配置时退化关键词；向量全表扫描数据量大后 O(n) 成本上升——这是项目规模下可接受的简化。

**Q3：为什么任务结束不直接写长期记忆，要走 pending 队列 + 定时批处理？**
答：两点。一是**避免每轮任务直接污染长期记忆**——低质量/失败/闲聊事件可能写进脏记忆，所以先入 `.memory-evolution-pending.jsonl`，由定时任务统一过滤（置信度≥0.55、敏感词拒收、按标题去重）后再合并。二是**合并要控制上下文预算**：`compactGlobalMemory` 按 16K 字符压缩，每节只保留最近 18 条，超预算按"节骨架优先、逐条贪心"裁剪。`shouldSkipRunRecording` 还跳过"记忆进化任务自身"的递归记录。

**Q4：相册增量扫描怎么保证不重复、不丢图？**
答：用 `AlbumScanCursor` 双字段游标（`DATE_MODIFIED` 时间戳 + `_ID`），查询条件 `(modified > t) OR (modified = t AND _id > id)`，避免同秒多张图片丢失；按从新到旧排序每批扫 20 张，遍历完一批把 `(时间, mediaId)` 最大值推进游标并持久化到 MMKV。以 `displayName` 为主键做去重。`force_rescan=true` 可重置游标全量重扫。

**Q5：图片隐私怎么防泄漏？**
答：三道防线。①摘要侧：VLM 的 system prompt 明确要求"避免输出身份证号、手机号、银行卡号、验证码、订单号等敏感字段"；②落盘侧：`ImageMemoryPrivacyFilter` 正则把身份证/手机/银行卡/邮箱替换为 `[REDACTED]`，命中高风险关键词（支付/转账/密码/住址…）判 `sensitivity=high`，只保留安全摘要；③画像侧：`MemoryEvolutionPolicy.isSensitive` 对密码/验证码/token/api key/secret 类候选直接拒收，`derivePrivacyAndRiskNotes` 把风险主题写进画像的 avoidTopics。

**Q6：token/上下文预算怎么控制？超了怎么办？**
答：分层控制。写入侧 `ChunkUtils` 用 `tokens*4` 字符估算分块（400 token、80 overlap）；注入侧 `ContextBuilder` 设 20K/文件、150K 总预算，超预算用"头 80% + 尾 20% + 省略标记"裁剪，USER-PROFILE 只注入 `Recent Signals Details` 之前的稳定画像部分，其余靠 memory_search/memory_get 按需读取；长期侧 `compactGlobalMemory` 保证 MEMORY.md 不超 16K。
